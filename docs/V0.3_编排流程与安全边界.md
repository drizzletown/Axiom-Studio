# V0.3 软件构造流程编排契约

## 工程对象

`Project`: name / goal / spec / manifest / baseline SHA-256 / parent_id / revision / status / candidate_id / verification / decision。

`Event`: immutable append-only record of workflow action (kind, payload, timestamp, predecessor hash, entry hash). The on-disk event chain is a local tamper *indicator*. It is **not** a cryptographic signature or externally trusted timestamp, and a user with DB file write access may forge an entire new chain.

`Proposal`: immutable candidate delegated to the pre-existing review-gated candidate store; its source, specs, manifest and protected files are hash-bound. The orchestrator never edits source itself.

`Evidence`: existing engine artifacts and the candidate-specific evidence directory, not browser-provided claims.

`Decision`: explicit, hash-confirmed human **test-only** acceptance following a fresh independent implementation Gate.

## State machine

```
draft -> (check -> plan -> verify -> model Gate) -> spec_ready
                                        |-> spec_blocked
spec_ready -> attach staged candidate -> candidate_review
candidate_review -> external review -> candidate_apply
candidate_apply -> external apply -> candidate_validate
candidate_validate -> external independent validation -> decision_pending | blocked
decision_pending -> live cpp-project-gate + human confirmation -> accepted_test_only
ANY project whose pinned specification or manifest changes -> effective stale
stale -> fork new revision -> draft (no inherited approval)
```

Every mutation is persisted in SQLite and the corresponding process event is hashed with its immediate predecessor. No transition infers approval from an AI response. The orchestrator reads the existing P2h verification CLI and review-gated candidate store; the UI does not fabricate test reports.

## Integration / architectural boundaries

- `studio/orchestrator.py`: trusted local workflow control plane, independent of editor HTML.
- `studio/server.py`: loopback HTTP transport, token required, declarative white-listed API.
- `studio/proposals.py`: unchanged candidate review/approval/evidence path.
- `engine/`: original Axiom semantic model and independent test/Gate tools.
- `studio/static/projects.js`: project status and human decisions. No code generation logic.
- `Axiom-Studio.code-workspace`: VS Code folder/task adapter, without bundling or forking VS Code.

Limitations: local SQLite/event hashes do not replace externally attested audit signing; no crash-recovery queue or distributed actor permissions; C++ candidate run requires separate local trust consent; production deployment deliberately unsupported.
