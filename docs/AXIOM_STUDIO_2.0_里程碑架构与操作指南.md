# Axiom Studio 2.0 · 软件生产里程碑架构

## 新范式的任务分工

**用户**：目标、验收场景、规则确认、重要权衡、原生代码执行授权及软件演化裁决。

**AI 构造者**：基于冻结任务包生成候选实现；不能改变受保护的规格、测试、Gate 或证据。

**AI 复核者**：提供风险及测试建议；其判断不能替代验证。

**Axiom 语义验证器和 C++ 工具**：通过实际规格模型检查、C++ 工程测试与 Gate 产生独立受界定的证据。

**Axiom Studio**：统一管理输入、任务、候选、验证批次、证据、依赖与迭代，确保变更失效与工作交接。

## 2.0 交付验证计划

模型 `plan` 绑定：`project_id`、`revision`、`baseline`、`contract_digest`、`manifest`、`spec`、每个文件的 SHA-256、测试依赖清单、前一验证批次、变化集合与预计受影响测试。每个执行阶段再次核对快照。

`changed_files` 是纯静态差异，`impacted_tests` 是**保守提示而非准入结论**。真实复用仅由引擎 `cpp-project-verify` 决定，并依据当前规格 IR、文件及传递头文件依赖、编译器二进制、验证器代码版本、编译选项和预期测试输出核对证据。

## 验证批次状态

`planned` → 经人工授信 → `running` → `passed` 或 `blocked`。批次不可再次执行；重试需重新创建批次，不覆盖已产生的失败证据。无授权、规格/代码漂移、Gate 失败、工具超时或审计异常均拒绝通过。

验证流程固定：`verify(spec)` → `gate(spec, model)` → `cpp-project-verify(manifest)` → `cpp-project-gate(manifest)`。工程集成测试每次重新执行。

## 安全与可用性

- 默认服务监听回环地址，API 使用会话 token，非多用户发布服务。
- AI 代码不得在 AI 生成阶段直接执行；生成与人工审核、验证授权分离。
- 验证进程采用超时及子进程组终止策略，**但不能据此宣称完整系统调用或文件系统隔离**。
- 本地 SHA-256 链可检查文件或结果篡改，不能阻止同机高权限攻击者重写全部记录。
- Axiom 模型检查和工程测试仍有覆盖边界，需继续通过真实工程量化任务完成率、人工操作成本与增量验收收益。

## 后续演化

2.x 将重点推进安全沙箱、可信执行证明、证据签署、跨语言验证适配、多模块并行集成及真实项目性能基准。优先处理已知历史联合测试超时，避免以数量增长掩盖可靠性问题。
