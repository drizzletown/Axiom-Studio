# Axiom Studio V0.6：多目标构造事务与方案比较

## 产品基线（保持冻结）

Axiom Studio 不重复制造已有的软件开发工具，而是把 AI、程序构造、行为规格、独立验证、可信证据与持续演化组织为完整的软件工程体系。代码编辑与调试继续复用 VS Code；Studio 主要负责生产契约、工作流控制、独立证据与人工裁决。

## 本版本实现范围

V0.6 新增 `studio/batches.py`，面向已冻结需求—性质映射且已通过模型 Gate 的项目，支持 **2～6 个 C++ 源文件组成一个候选方案**，同一事务最多比较 6 套完整替换方案。当前受原 Axiom `ax-cpp-project/0.1` 工程清单约束，要求平坦、完全列举、无符号链接的项目目录；`.ax`、`project.json`、头文件与测试均不可作为候选修改目标。

1. **冻结构造输入**：绑定当前项目版本、冻结的生产契约、任务包、规格、清单和所有受保护源码摘要。
2. **完整方案暂存**：每套替代方案应一次提供所有目标 `.cpp` 的完整源代码；代码写入 SHA-256 内容寻址对象，而不是覆盖源码。
3. **真实影子验证**：独立复制当前受保护输入并应用整套替代方案，分别运行有限状态模型验证、模型 Gate、C++ 全量单元/集成测试与实现 Gate。各备选方案使用独立证据库；没有编译执行授权就不会运行 C++。
4. **人工作出方案选择**：清晰展示被拒绝的测试目标、Gate 结论和候选摘要；Studio 不把耗时或通过情况变成默认的“最优”自动裁决。
5. **可恢复的整体应用**：人工确认后，将完整项目目录阶段化并保存原始目录备份，通过受控目录切换安装多个源码文件。保留事务记录和崩溃恢复入口。它是**可恢复目录切换**，不是跨文件系统的严格原子事务。
6. **实际工程重新验证**：应用后再次使用独立证据库完整验证真实工作区，不能直接把影子验证结果当作已安装工程的准入依据。失败时尝试安全回滚，若发生外部文件修改则中止覆盖，改由人工恢复。
7. **人工测试级准入**：最终独立重新调用当前工程 Gate，正确且指纹匹配时只记录 `accepted_test_only`，永不授权生产发布。
8. **失败反馈**：为已失败候选提供结构化诊断任务包，可交给第三方 AI/VS Code 编写新方案，但禁止未经审查的自动重试、篡改测试或放宽规格。

## 主要接口

- `POST /api/batch/create`：`{project_id, targets:["cpp_project/ledger.cpp","cpp_project/format.cpp"]}`
- `POST /api/batch/stage`：`{id, name, replacements:{"ledger.cpp":"...", "format.cpp":"..."}}`
- `POST /api/batch/evaluate`：`{id,option_id,trusted:true}`（同步执行；须确认源码可信）
- `GET /api/batch/compare?id=...`：真实证据与受约束的多方案比较
- `GET /api/batch/repair?id=...&option_id=...`：失败反馈任务包
- `POST /api/batch/select`：`{id,option_id,digest,confirmation:"human_selected_after_comparison"}`
- `POST /api/batch/apply`：`{id,digest,confirmation:"human_authorized_multi_file_apply"}`
- `POST /api/batch/verify-live`：`{id,trusted:true}`
- `POST /api/batch/decide`：`{id,digest,confirmation:"human_approve_test_only"}`
- `POST /api/batch/rollback`：`{id,confirmation:"human_reject_and_rollback"}`
- `GET /api/batch/list?project_id=...`、`GET /api/batch/get?id=...`、`GET /api/batch/audit?id=...`

这些 API 继承原 Studio 的本地令牌保护，不构成企业级身份或权限体系。

## 可重现测试

```bash
python -m pip install -r requirements.txt
PYTHONPATH=studio:engine/src pytest -q studio/tests/test_batches.py studio/tests/test_batches_http.py
# 实际 C++ 编译/执行；只在经信任的 Linux/WSL2 环境运行
PYTHONPATH=studio:engine/src python scripts/batch_demo.py --output studio/batch_demo_report.json
```

V0.6 完整示例用 `ledger.cpp` 与 `format.cpp` 作为同一构造目标组；“正确的双文件方案”通过独立影子验证和工作区重新验证，故意把收据起点与终点调换的方案由真实 C++ 测试拒绝。测试覆盖受限 C++ 构造场景，不构成真实软件总体正确性的形式化证明。

## 未解决问题及技术债

- 生产环境中不能把目前实验性 Linux Namespace 隔离视作运行不可信 AI 代码的充分安全保障；禁止将未经审查的恶意源码交给当前执行环境。
- 本地 SHA-256 记录和哈希串接审计无法抵御拥有工作目录写权限的恶意用户；独立签名者、远端/不可变存储尚未部署。
- 方案来源支持人工输入及外部工具提供的 JSON；多 Agent 自主规划、AI 自动生成完整多文件方案、正式数字身份审批及跨项目依赖仍未完成。
- 当前目录切换要求备份和工作区处于同一文件系统；进程崩溃、开放文件句柄、权限和并发编辑可能需要人工恢复。当前不具备生产级 ACID 事务保证。
- 旧版全量测试仍会偶发超时，本阶段验收统计仅包括明确完成的专项、兼容和真实端到端用例。
- `accepted_test_only` 与原 V0.5 单目标项目护照不同；尚未将多方案事务自动提升为原项目的正式发布依据。

下阶段优先建设并行执行的构造任务图、可验证的跨模型候选来源身份、异步故障反馈循环和远端独立证据服务。产品定位保持冻结。
